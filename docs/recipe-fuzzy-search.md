# 离线分词、拼音与容错检索

这层实现位于 `backend/src/recipe-search-core.ts`，同步镜像为 `client/entry/src/main/ets/model/RecipeSearchCore.ets`。原 RecipeDiscoveryCore.searchRecipe 保留精确检索接口，页面应使用本层全集检索来获得分词、拼音、容错和显式推荐状态。无需云服务、在线模型或新增运行时依赖。

## 词典与读音的来源

分词词典由当前菜谱的名称、别名、原料、地区、菜系自动生成，新增菜谱也自动加入。少量烹调词和既有同菜做法名称补充边界线索，不为用户每一种输入编写固定句子。字典分词使用动态规划，最大化已知字符覆盖并偏好完整词；不丢弃无法识别的字。忽略单字词边界，防止“鸡旦”被拆为“鸡”和“旦”而失去整体同音纠错机会；查询单字仍能做原有子串匹配。

拼音读音来自通用汉字字符表：20,924 个字、411 个音节、约 66 KB 源数据。不是每道菜各存一份拼音，也不随截图/导出重复保存。`scripts/generate-search-pinyin.py` 用 macOS 自带 CoreFoundation/ICU 可再生成，手机和后端只读生成的 TypeScript/ArkTS 数据，不依赖 macOS。食物语境补充茄→qie、长→chang，以及重庆、薄荷、朝天椒等少量多音上下文。生僻扩展字没有读音时保留不完整状态，不将其当通配符。

## 检索层级

1. 精确搜索：保留原来的菜名/别名/原料/地区相关度及空白、大小写、全半角处理。
2. 自动分词：例如 `番茄鸡蛋` → `番茄`、`鸡蛋`，各词都须命中。`番茄 牛肉` 在只有番茄时不能伪称完整命中。
3. 拼音搜索：支持全拼、分音节空格、声调字母/数字、首字母与中英混输，例如 `fanqiechaodan`、`xi hong shi chao ji dan`、`fqcd`、`番茄jidan`。连写的多个原料拼音可按生成词典拆分，例如 `fanqiejidan`。
4. 同音与错字：汉字查询也转换读音，`宫爆鸡丁` 可匹配宫保鸡丁，`鸡旦` 可匹配鸡蛋。额外采用有界 Damerau-Levenshtein 距离，支持增删改与相邻字母颠倒。中文至少三字才允许无读音证据的编辑纠错；三至七字最多一处，八字及以上最多两处。拼音至少五字母才做编辑纠错，五至八字母最多一处，九字母起最多两处。两字词仅因共享“肉/菜”不互相替换，牛肉不会被改成鸡肉。

完整匹配必须满足所有分词。排序层级为精确 > 分词 > 拼音 > 错字，分别以 8000、6000、4000、2000 为底分，再附带字段相关度。含多个词时取最弱命中层级，避免一个强命中掩盖另一个弱猜测。每个结果保留 level 和 reasons。

## 无直接匹配的状态

当受限候选中没有完整匹配，返回 `mode=similar`，不修改原输入、不将推荐伪称搜索命中。优先参考部分关键词、查询明确菜系、真实匹配菜谱的菜系及调用方显式偏好。同菜系优先；川湘、粤闽浙、鲁苏徽之间仅作为产品层面的口味邻近导航，不声称传统菜系标准。

有相应依据与可用菜谱时显示“没有找到完全匹配的结果，为你推荐相似菜系”；乱码或其他完全无依据的输入显示“没有找到匹配结果，先看看这些家常菜灵感”。默认最多 12 条，调用参数限在 1–30 条。若硬筛选后本来没有任何菜，则返回 `mode=empty`，说明可以调整筛选，不能为了非空放宽忌口、时间、库存或收藏限制。空查询返回 `mode=all`，不限制完整列表条数。

## 页面调用

```ts
// candidates 必须先通过既有硬筛选、忌口和收藏等约束，不能先按旧文本搜索裁掉。
const result = searchRecipeCandidates(candidates, query, preferredCuisines, 12);
// result.mode: all / matched / similar / empty
// result.recipes: candidates 内的原始对象引用
// result.hits: recipeId / score / level / reasons / matchedTerms
// result.tokens / message / suggestedCuisines
```

保留页面 Recipe 类型时，可按 hits.recipeId 从原 candidates 取对象并按 hits.score 排相关度。不能继续用旧 compareRecipeOrder 的精确搜索分数覆盖拼音/模糊相关度。用户显式选择价格/耗时则仍使用该排序；推荐页相关度同分可保留原推荐序。

大目录可在菜谱变动时缓存 `new RecipeSearchIndex(recipes)`，查询调用 `searchRecipeCatalog(index,query,eligibleIds,12,preferredCuisines)`；eligibleIds 为严格允许清单，空数组表示没有候选，不是“不限”。该方式可用完整目录推断搜索线索，但返回对象始终属于允许清单。

提示可在输入时页内显示，在提交搜索时 toast 一次，避免每输入一个字反复弹窗。不要自动把输入框改成算法猜测的词。

## 验证和边界

在 backend 运行 `node --import tsx test/recipe-search.test.ts`。该测试已通过，覆盖真实 450 条目录、多种输入、精确优先、自动新增词典、错字限制、筛选/忌口保留、原对象引用、稳定顺序及实际 ArkTS 镜像依赖图执行一致性。开发机实测建索引约 18–33 ms，常见查询约 4–20 ms；原生设备表现以主开发的整包构建和交互验证为准。

这仍是本地词典与读音容错，不是语言模型语义理解；不保证任意错字、多音字、方言读音或整句需求都能理解。生成读音表无需反复维护每道菜，但通用字音仍需要少量食物语境修正。此层尚不改变 GET /catalog/recipes 的 SQL 查询范围；HTTP 搜索已知边界见 recipe-discovery.md。

## 本轮相关度和明确需求改进

新增 `backend/src/recipe-query-intent.ts` / `RecipeQueryIntent.ets`。`searchRecipeCatalog` 和 `searchRecipeCandidates` 调用参数保持不变；结果新增带默认值的 `intent`，命中新增规则置信度 `confidence`，原页面可直接继续使用。

支持明确表达：不辣/不要辣；不要、不吃、不放、不加、不含某原料；有/用/含有某原料；“有鸡蛋没番茄”；十分钟内、半小时内、一小时以内、不超过十五分钟等。原料列表支持连接词及空白。这些解析成额外硬条件，先与调用方允许 ID 求交，再进行召回和补充推荐。只包含条件的搜索可直接返回符合条件的完整列表。

时间未知不能满足时间上限，口味未知不能声明不辣，原料缺失不能满足“有某原料”。可选调料同样参与排除，花生排除也检查花生油等复合名称。无法确认的明确原料要求、包含/排除冲突及无效时间返回说明，不通过推荐绕过。这里检查的是已记录原料及口味，不推断未标注的隐藏配料或营养成分。

相关度新增 BM25 启发的逆文档频率和名称长度归一，不声称完整实现 BM25：

```text
词权重 = 1 + 0.25 × min(4, ln(1 + (N - df + 0.5) / (df + 0.5)))
名称归一 = 0.75 + 0.25 / (0.6 + 0.4 × 名称长度 / 平均名称长度)
```

df 为包含该词的菜谱数，一道菜的多个别名或重复原料只计一次。词在少量菜里出现时更有辨识力；主料字段加权 12、可选调料 4；名称/别名分别 24/20。精确、分词、拼音、错字的分层底分仍保留，新增权重不会把模糊结果推到精确结果之上。

首字母前缀至少三字母且覆盖目标首字母长度的 60%；两个字母仍要求完整首字母匹配。词频及置信度用于规则排序，不是经过统计校准的正确概率。拼音两处容错只用于至少九字母、首字母相同的菜名/别名；原料拼音最多一处，减少把整个菜名近似成某个普通原料的问题。菜系字段不做无读音证据的编辑纠错。

固定评测集为 `backend/test/search-evaluation-cases.json`，包含 30 条精确、拼音、错字、无关输入和明确条件查询。命令：

```sh
node --import tsx scripts/evaluate-search.ts ../work/reports/search-evaluation-after.json --check
node --import tsx test/recipe-query-intent.test.ts
```

本轮固定样本通过数从 21/30 提升到 30/30，已标注的名称查询前三条召回与 MRR 均保持 1，明确条件样本符合率从 0 提升到 1。详见 `work/reports/search-evaluation-before.json` 与 `search-evaluation-after.json`。这是小样本回归结果，不能代表任意真实输入的准确率。新增边界测试验证未知数据、可选辣椒、冲突条件、主料优先和实际 ArkTS 镜像依赖图一致性；七套算法回归与 TypeScript 类型检查通过。
