量、火候和时间属于编辑参考，不能表述为某平台作者实测。所有新增热量、蛋白质均为未知 -1，costKnown=false，不能将未知展示为 0 大卡或零元。高蛋白标签是依主要食材的搭配建议，不是营养测定或减重处方。肉类使用熟度与温度确认，菌菇/豆类写充分熟制，生熟器具分开。

## 可落地的实用性方向

1. **待做清单/稍后做**：收藏与今天开做分开，菜谱详情一键加入，再按食材可用性排序；借鉴 Mealie 的计划流，而非再加一层“教程”页面。
2. **菜谱到购物清单**：只列库存不足量，同名食材合并，克/千克等兼容单位换算；勾选已买后进入入库表，不让勾选直接伪造库存。
3. **最近做过/最近吃过**：读真实记餐与做菜记录，允许直接再做并预填人数，减少重新搜索；仅浏览做法不计入做过。
4. **餐次快速筛选与保存条件**：早餐午晚加餐为独立多选；草稿与应用分开，重置必须可预期，不把推荐推断当来源元数据。
5. **逐步烹饪/自动锁屏保持**：长步骤专注模式，只在用户点“做完”后考虑扣库存；倒计时需要独立暂停/恢复，离开页面不静默丢失。
6. **一周计划**：先本地草稿，按日/餐次插入菜，支持一键换菜；多人合餐重复食材在购物清单合并。
7. **单位和食材别名**：主食干熟重不可等同；豆腐品类不可一概替换，未知量不强行判断“主料够用”。

上述是公开产品研究后的本项目独立实现方向，不代表所有方向已接入原生客户端。实际已实现内容以主任务验收为准。

## 重建与验证

运行 `python3 scripts/expand-recipe-library-v3.py` 会按稳定 UUID 补入 64 道，拒绝覆盖已存在的不同来源同名菜，自动调用既有统一教程编排器并同步 rawfile。再次运行不新增重复菜。运行目录 backend 下的 `node --import tsx test/recipe-expansion.test.ts`、`test/usability.test.ts`、`test/recipe-filter.test.ts` 验证目录镜像、数量、未知营养、原料/器具、完整统一步骤、实际餐次筛选和抽菜约束。所有新增图的请求清单在 work/reports/recipe-expansion-image-request.json，包含稳定 ID 和建议文件名。
