# 菜谱来源、人数与口味推荐

当前内置扩展库386道，加上原先4道离线菜谱，原生客户端显示390道。类别含家常、快手（不超过20分钟的计划估时）、汤、粥、主食、早餐、凉菜、甜点和大菜；地区覆盖不均，不能声称覆盖所有菜系。减脂餐、高蛋白是编辑标签，不代表医学或营养处方。

## 用量推荐

所有量都供制作前参考，不表示固定标准。页面保留来源用量原文，区分基于菜谱的换算与缺失分量的推荐估算。

1. 人数1–20，食量小/正常/大分别为0.75/1/1.25。
2. 已知主料按目标人数÷基准人数×食量换算；每次从原始菜谱计算，避免重复放大。来源未说明人数时，基准人数是估计，页面明确提示。
3. 调味料按人数比例的0.8次幂缓增；清淡口味将盐、酱油等缩至70%，食用油缩至80%；浓郁口味相应调味增加至115%。这是体验性启发规则，不是专业定量结论。
4. 辣度可独立选原方/不辣/微辣/重辣，对可识别辣椒类分别应用1/0/0.5/1.4系数；调味料应试味后添加。
5. 缺失分量根据可识别食材的经验量推算，例如肉类约150g/人、蔬菜约200g/人，在同类主料间分配。适用一餐中的一道菜，应按其他菜品再减量。无法识别的食材仍显示待填写，不把0当作有效制作量。
6. 预览本身不改菜谱、不改库存；“应用推荐到本次制作”只更新草稿；“确认制作”再走原有事务扣库存与记餐。调味料单独展示，不自动扣库存。

共享实现为 `backend/src/portion-core.ts` 和客户端 `PortionCore.ets`。后端预览接口 `GET /api/v1/catalog/recipes/:id/portions?people=4&appetite=1&seasoning=清淡&spice=微辣` 需登录，只读。

## 本地个性化

账号资料的地区映射为菜系偏好（如重庆→四川、辽宁→东北），饮食目标作为后端推荐缺省值；请求显式参数优先。客户端登录和保存资料后同步更新本机推荐偏好。

推荐先过滤忌口、口味、地区、分类等硬条件，再综合库存覆盖、临期、地区偏好、近期重复和饮食目标。轻量统计模型从最近180天的可识别用餐记录及90天的喜欢/少推荐等反馈中学习地区、口味和分类偏好，并按时间衰减；同菜同日去重。关闭学习后不使用学习分数。不能仅凭照片自动判断菜名或热量。

用餐记录支持在家做、外卖、餐馆、食堂、可选地点、1–5星评分、实付/估算花费和示例主体实际摄入热量。未知热量存为-1，不作为零热量。用户自行记录的热量为估算；不会把整锅人数乘出的热量自动算到单示例主体头上。

## 做法优先与耗时推荐（本轮）

详情默认先呈现耗时与完整步骤；人数、口味和用料换算折叠，来源仍可展开溯源。专注模式只切换阅读步骤，不自动扣库存或记餐。总耗时优先使用菜谱minutes；缺少总值时才用有效备料/制作时间求和；拆分时长与总值不一致时只展示总值，不补造备料时间。所有耗时为参考。

时间预算15/30/60分钟是硬筛选，未知耗时不进入限时结果；可选耗时优先排序。推荐模式cook保留库存/临期权重，record不使用库存/临期得分，继续参考地区、饮食目标、历史和反馈。1–2星餐次对匹配菜谱特征给负权重，4–5星给较高正权重；只对可识别菜名/ID学习。近7天直接“少推荐”额外降权，关闭学习同时关闭评分和反馈学习。前12条增加同类主料重复惩罚；换批只改变有界探索顺序，不把整批未点菜自动记成负反馈。
