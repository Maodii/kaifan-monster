# 上线后体验优化方向

按真实影响排序，先稳定核心流程，再扩大功能。没有数据之前不设置虚假的留存/成功率基线。

| 优先级 | 方向 | 判断依据与下一步 |
|---|---|---|
| P0 | 失败与慢请求 | 按看板异常Top20修复；分别看AI模型回答率、P95、额度触发，不把业务降级当作HTTP成功。补充客户端网络错误与崩溃监控，提供请求编号。 |
| P0 | 账号找回 | 管理端已支持核实归属后重置；配置真实邮件/短信及发送状态后再开放自助找回。当前生产邮件投递未配置，不应显示假成功。 |
| P0 | AI质量与安全 | 发布回答评价入口，优先处理“不准确/不相关”；维护不含真实隐私的回归题集，覆盖过敏原、库存、做法和记餐。不直接把用户聊天全部存入分析库。 |
| P1 | 成本与容量 | 从供应商真实usage接入输入/输出Token、模型名及账单对账；流式usage需单独处理结束帧，缺失记未知而非0。先测10人同时使用的首字/P95/失败率，再决定CPU、内存、带宽或供应商配额调整。 |
| P1 | 体验漏斗 | 在用户明确知情及可控制的前提下增加客户端启动、提问发送/取消/重试、照片选择至上传完成、草稿采纳等少量事件；端到端计时与服务端分开。排除自动同步，避免把后台流量当主动使用。 |
| P1 | 留存与额度 | 在客户端活跃事件可靠后统计次日/7日留存；观察普通用户触发50次上限的比例和有效回答率，再调整额度。看板云端活跃不能直接替代全端留存。 |
| P1 | 弱网与恢复 | 检查图片压缩/断点或受控重试、离线草稿、失败提示与取消体验；保留请求幂等性，避免重试重复扣额度和重复写记录。 |
| P2 | 管理效率 | 真实运营需求出现后增加分级运营角色、异常工单、受控导出和告警；敏感操作继续保留身份复核与审计。 |

建议发布后先观察一周，再按用户数与样本量调整计划。没有足够样本时不要用几个测试账号判断留存，也不要仅凭服务器内存空闲就承诺可承载人数。旧服务器目前仍负责旧版客户端转发，迁移覆盖确认前保持运行。

尚未接入：Token/费用、客户端崩溃、页面访问、完整转化漏斗、次日/7日留存、自动统计异常通知。已有服务器健康检查继续运行；本任务未创建新的付费服务、定时自动化或应用商店发布。

2026-11-17补充：双端已接入独立默认关闭的可选行为统计（前台、页面、AI发送/重试/取消/完成、用餐图片上传），管理端已提供逐用户每日AI次数设置。客户端上线后可基于自愿开启的样本观察流程；未开启与本机用户不纳入，仍不能直接当作完整DAU/留存。真实Token账单、客户端崩溃与完整留存尚未接入。
