你是资深全栈工程师，从零构建完整项目：项目名称「食库」。
整体定位：鸿蒙 Next（ArkTS）客户端 + 后端服务。遵循 “本地优先，云端增强”。所有核心业务断网必须完整可用；云端只负责备份、同步、条码模板库、菜谱库、推荐、社区、图片托管、多设备、家庭共享；服务器宕机或者无网络，客户端不能崩溃，不能丢失已录入数据。

后端栈：使用 Node.js + NestJS + TypeScript。数据库 PostgreSQL；Redis 用作缓存、锁、热门数据；图片、菜谱配图、用餐照片全部存入对象存储（MinIO / COS / OBS），数据库只保存访问链接，禁止在数据库或服务器本地目录存放二进制图片。

整体原则：
1. 客户端：HarmonyOS Next，纯 ArkTS，原生组件、原生 RDB、Preferences、Notification、ArkTS Card、Scan Kit、相机、相册、文件沙箱。不使用 WebView，不引入重型第三方 UI 库。
2. 后端：NestJS，TypeScript，模块化，强类型；提供 REST API，全部接口支持 HTTPS；所有写操作携带用户 ID、设备 ID；鉴权失败直接拒绝。
3. 同步机制：全部变更采用 “变更日志 + 版本号 + 设备 ID + UTC 修改时间戳”。客户端每一次增、改、删，生成本地变更记录；联网后上传变更日志；服务端维护每个用户的全局版本；客户端拉取大于本地版本的变更，增量合并。冲突策略：默认以较新时间戳覆盖；如果同一条记录两端同时修改，返回冲突，客户端弹出选择，由用户决定保留或者合并。
4. 用户、设备、家庭：注册、登录，使用 JWT（access token + refresh token）；设备绑定、解绑；家庭组，邀请码加入；区分示例主体空间和家庭共享空间；权限隔离：普通成员读写，管理员增删成员、解散组。
5. “自动操作”（自动扣库存、自动推荐、自动加入采购）全部必须展示确认弹窗，不能静默执行，防止误操作。
6. 条码扫码：不依赖外部第三方商品库。扫码仅作为预填充辅助。调用 Scan Kit 获取条码；优先查本地私有条码模板；本地没有再请求后端自建条码库；命中之后预填充名称、分类、默认保质期天数、推荐存放位置；无论是否命中，都进入可编辑确认表单，用户确认之后才保存；用户可选择保存当前填写内容作为条码模板，供自己、家庭，或者提交公共库等待管理员审核。散装、农贸市场、自制食材使用内置预设食材模板快速录入。
7. “价格、成本、预估花费” 全部标记为估算值，不作为精确财务记账。
8. “禁止任何调用大模型、生成式 AI、外部智能推理服务。所有推荐、筛选、排序、匹配全部用确定性业务规则，没有任何 AI 分支、备用 AI 通路、或者可选开关接入模型。”

## 模块 3：菜谱、教程、今日吃什么推荐

页面：今日推荐页、菜谱详情页、菜谱广场、下厨模式。

今日吃什么（推荐）
- “只使用确定性规则，完全禁止调用任何 AI、大模型、外部生成服务。”
- “权重顺序（从高到低）：
  1. “菜谱包含至少一件临期食材（最高权重，优先消耗即将过期食材）”
  2. “匹配当前冰箱已有食材数量（匹配越多，排名越高）”
  3. “满足用户硬性过滤规则：排除忌口食材，匹配所选口味（清淡 / 香辣 / 酸甜）”
  4. “排除或者降低最近 N 天已经吃过的菜谱，减少重复推荐”
- “计算“缺失食材清单”：列出这道菜里冰箱没有的原料，标明还差哪些。清晰展示缺材列表，并提供一键全部添加到采购清单。”
- “选用这道菜：进入确认弹窗，如果确认制作，按菜谱用料自动扣减冰箱食材；用户可以修改实际消耗数量再确认。”
- “一键换一批：在当前筛选和权重范围内重新取样另一组候选菜谱。”
- “用户偏好设置：忌口（海鲜、内脏）；口味（清淡、香辣、酸甜）；排除最近吃过的菜（可配置天数）。”
- “离线降级：当没有网络或者推荐服务不可用时，直接在本地预置菜谱库内运行完全相同这套权重与筛选规则，保证行为一致。”

菜谱数据结构
- “菜谱基础信息：菜名、菜系分类、口味、难度、预估制作时长、适合人数、参考总成本、作者、发布状态（草稿 / 待审 / 已发布 / 私有）。”
- “菜谱用料列表：食材名称、数量、单位；绑定系统食材，用于匹配冰箱库存和自动扣减。”
- “分步教程：顺序编号、步骤文字描述、可选配图链接；支持 “下厨模式”，每一步标记为已完成，自动跳到下一步。”
- “烹饪计时：支持多阶段计时（焯水、大火、小火、焖泡），调用系统定时器，振动 + 声音提醒。”
- “小贴士：火候、调味、替代食材、保存建议。”
- “收藏菜谱；收藏同步云端。”

菜谱广场
- “浏览公共菜谱；搜索；筛选：菜系、难度、耗时、价格区间、热门、最新。”
- “查看示例主体菜谱草稿；提交新菜谱到社区，进入待审核队列。”
- “如果是家庭组，查看家庭共享菜谱。”

6. “可见范围严格隔离；默认私有；公开发布必须二次确认；价格对外默认隐藏。”
7. “推荐只使用确定性业务规则：优先临期食材，再匹配库存，再过滤口味、忌口，再避开近期已吃菜谱。禁止任何 AI、模型调用，没有降级到 AI 的分支。”
8. “后端可部署到轻量虚拟云服务器；提供 Docker Compose、环境变量、部署文档。”
9. “闭环完整：冰箱库存 → 推荐菜谱 → 查看教程 → 确认制作（扣库存） → 拍照记录用餐 →（可选）发布家庭或公开社区；代码适合实习作品集，命名清晰，注释区分优先级。”

## 禁止事项
不要做这些：
- “不要把云端作为强依赖，断网后核心功能失效。”
- “不要调用外部免费条码库作为核心逻辑。”
- “不要静默保存、静默扣库存。”
- “不要保存图片二进制到数据库或服务器本地。”
- “不要使用旧版鸿蒙，不要生成 Web、Flutter、React Native；客户端目标是 HarmonyOS Next，ArkTS。”
- “不要忽略冲突，直接盲目覆盖用户数据。”
- “不要把预估花费做成精确财务系统。”
- “不要省略加载、空状态、错误、权限处理。”
- “不要跳过审核，直接把用户提交菜谱、动态转为公开。”
- “严禁加入任何大模型、生成式 AI、外部智能服务调用、配置开关、占位注释或者备选通路。整个项目是纯传统服务端 + 客户端应用，没有任何 AI 部署。”

## 最后要求
优先产出 MVP（P0），之后追加 P1、P2；拆成可开关模块；输出工程目录、接口清单、鸿蒙路由、数据库迁移脚本、Docker Compose、部署文档；保证本地可运行，之后部署到虚拟云服务器，作为完整作品集项目。所有推荐、匹配、排序全部是硬编码业务规则，没有任何人工智能组件。

## 用户后续范围补充（优先于最初不使用AI的限制）

允许本地轻量统计学习，从每天记录、地区与口味反馈优化推荐；不等于要求外部大模型或照片自动识别。先完成本地版本。增加大众平台来源菜谱、地区/类别/减脂餐、多人数和口味差异化推荐分量，所有量均为建议；缺失用量明确标注预测。支持不做饭者记录外卖/食堂/餐馆、可选地点、实付金额、味道评分和示例主体热量。来源受限时如实记录，不编造采集成果。
